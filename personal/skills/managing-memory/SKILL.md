# 长期记忆管理

统一「跨会话长期记忆」的存放位置、文件格式与读写流程，配合 `memory-sync` 规则使用。
规则管「何时必须读写」，本 skill 管「具体怎么做」。

## 流程清单

任务**开始前**（读）：

- [ ] 定位记忆库根目录（见「一、记忆库位置」）
- [ ] 读 `global/lessons.md`
- [ ] 按文件名与 `tags` 筛 `projects/<当前项目>/`，命中的完整阅读
- [ ] 对每个 `code_anchors` 读**当前仓库最新代码**交叉验证 ⚠️ 不可跳过
- [ ] 锚点已漂移的，记下「历史 vs 现状」差异，以最新代码为准

任务**完成后**（写）：

- [ ] 判断归属：跨项目会再犯 → `global/lessons.md`；本需求特有 → 项目记忆
- [ ] 全局教训：先找能归入的已有教训追加案例，覆盖不了才新增；标题与正确做法写抽象层
- [ ] 项目记忆：不引用全局教训编号，把坑的上下文写完整
- [ ] 写入前扫已有条目去重，语义重复的合并而非堆叠
- [ ] 同 slug 已存在则增量更新（含刷新 `updated` 与漂移的锚点），不新建重复文件
- [ ] 确认没写进密钥、凭据、大段代码原文
- [ ] `global/` 的 git 提交留给用户，不自动 commit

## 一、记忆库位置

记忆库在 ai-repository 仓库根下的 `memory/` 目录。定位方式（任选其一）：

1. 标准路径：`D:\hub\ai-repository\memory`（团队约定的 ai-repository 克隆位置）。
2. 运行解析脚本（跨机器稳健，推荐不确定时使用）：

   ```bash
   node <本 skill 目录>/resources/resolve-memory-root.js
   ```

   脚本从自身位置向上查找 ai-repository 根并打印 `memory` 绝对路径。
3. 若知道 ai-repository 位置：`node <ai-repository>/scripts/ai-config.js memory status`，
   会打印记忆库根目录、全局教训条目数、各项目记忆清单。

若 `memory/` 尚不存在，先执行 `node <ai-repository>/scripts/ai-config.js memory init` 初始化骨架。

## 二、目录与版本控制

```text
memory/
├── global/lessons.md              # 全局级：跨项目通用错误（提交进 git）
└── projects/<项目名>/<需求-slug>.md   # 业务需求级：核心逻辑/设计/该需求特有的坑（纳入版本库）
```

- 全局教训与项目记忆均随 git 跨机器同步。项目记忆里不得写入密钥、凭据、大段代码原文。
- `<项目名>` 用仓库目录名（如 `pac-platform`）；`<需求-slug>` 用短横线小写（如 `offline-approve-link-macro-whitelist`）。

## 三、业务需求级记忆格式

每个需求一个 `.md`，YAML front-matter 供机器筛选，正文供人阅读。模板见
`resources/project-memory.template.md`。字段约定：

- `id`：`<项目名>/<需求-slug>`
- `scope`：固定 `project`
- `project` / `feature`：项目名 / 需求 slug
- `updated`：最后更新日期 `YYYY-MM-DD`
- `tags`：主题关键词，便于检索
- `code_anchors`：**下次交叉验证的锚点**，逐条写 `path`+`symbol`、或 `table`、或 `apollo` 等；
  这是「记忆」与「最新代码」对齐的关键，务必写准确的文件路径与符号名。

正文四段固定：核心业务逻辑 / 核心代码设计 / 踩过的坑与反复纠错点 / 交叉验证提示。

## 四、读记忆 + 交叉验证流程

1. 读 `global/lessons.md`。
2. `list` 出 `projects/<当前项目>/` 下的 `.md`，按文件名与 front-matter `tags` 判断相关性，
   命中则完整阅读。
3. 对命中记忆的每个 `code_anchors`，读取**当前仓库最新代码**：
   - 锚点仍存在且语义一致 → 采纳历史结论。
   - 锚点已改动 / 消失 → 记录「历史 vs 现状」差异，以最新代码为准，动手前先消化差异。
4. 不要凭记忆断言现状；凡写入结论的类/方法/表/配置，都要在最新代码里确认存在。

## 五、写记忆流程

任务完成时：

1. **确定归属**：跨项目会再犯的错 → `global/lessons.md`；本需求的逻辑/设计/特有坑 → 项目记忆。
2. **项目记忆**：
   - 已存在同 slug 文件则**增量更新**（更新 `updated`、补充新坑、修正漂移的锚点），不新建重复文件。
   - 不存在则用模板新建。
   - **项目记忆自成体系，不引用全局教训编号**（全局教训会定期整理重组，引用会失效）。
   - 把踩坑的完整上下文、具体类名/方法/表/配置、改了几轮、为什么当时没发现等细节写清楚。
3. **全局教训**（格式见 `resources/global-lesson.template.md`）：
   - **一条教训对应一类问题，不是一次事故一条**。标题、「问题本质」「正确做法」写抽象层：
     标题如「工具输出不是事实本身，要取直接证据」，而不是「文件大小差 117 字节误判为换行转换」。
   - 「问题本质」写犯错的认知/习惯根因，回答「为什么会犯这类错」。
   - **具体事故写进「案例」**：每个案例保留当时的场景、反例（错在哪）、正例（该怎么做）和日期，
     可以匿名化，但要留下足够还原现场的细节（具体 API、命令、数值）。
   - 写入顺序：先找能归入的已有教训 → 追加案例 → 必要时修订其「问题本质 / 正确做法」使之覆盖新案例；
     现有教训都覆盖不了时才新增条目。
4. **去重与定期整理**：
   - 写入前先扫已有条目，语义重复的合并而非堆叠。
   - 全局教训会定期整理：合并同类教训、拆分过宽的教训、重排编号。整理时案例原样保留，
     只调整它们挂在哪条教训下。编号只用于本文件内部定位，不承诺稳定。
5. **提交**：只做本地文件写入，`global/` 的提交交给用户，不要自动 `git commit`。

## 六、注意

- 记忆是「经验」不是「事实快照」：正文可保留历史判断，但每次使用前都以最新代码为准做校验。
- 不要把密钥、凭据、大段代码原文塞进记忆；记锚点（路径+符号）和结论，用到时去读代码。
