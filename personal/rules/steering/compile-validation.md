# 构建与编译验证规则

## 默认策略

- 非必要不执行 Gradle 编译、构建或全量测试，优先使用文件诊断、类型检查、静态分析和针对性验证。
- 仅修改注释、文档、格式、日志文案或不影响 Java 编译结构的内容时，不执行编译。
- 同一轮连续修改多个文件时，合并修改完成后最多执行一次相关模块编译，不要每个文件单独编译。

## 需要编译的情况

- 用户明确要求编译、构建或验证编译结果。
- 新增或修改 Java 类、方法签名、接口、继承关系、package、import、实体字段或配置绑定，且仅靠诊断无法可靠确认兼容性。
- 移动或删除 Java 类，可能影响跨模块引用。
- 修改 Gradle 配置、依赖、插件、编译参数或生成代码配置。
- 交付前用户要求以编译通过作为验收标准，或诊断发现必须通过编译才能确认的问题。

## 汇报要求

- 未达到上述条件时，不主动编译；如用户需要，可说明未编译并给出建议命令。
- 编译耗时较长时，优先编译受影响的最小模块，不执行全量 build。
- 未执行编译时，不能声称“编译通过”；应明确说明实际执行的验证方式。
