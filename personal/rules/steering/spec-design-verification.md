# Spec 设计自校验规则

spec / 需求 / 设计类产出（requirements、design、方案对比、技术选型、接口与数据结构定义、任务拆分），在把结论回复给我或写入文档**之前**，必须先自己完整校验一遍，不要边想边输出。

## 输出结论前的自校验清单

1. **需求覆盖**：逐条回读需求文档，确认每条需求/验收标准在设计中都有对应落点；设计中出现但需求里没有的内容，标明来源或删掉。
2. **事实核对**：设计中引用的每个类、方法、字段、表结构、配置项、枚举值、第三方接口，都必须**实际读过代码/DDL/文档确认存在且语义一致**，不靠命名推断、不靠记忆、不靠"其他模块是这么写的"。无法确认的显式标注"未验证"，不要当成事实陈述。
3. **边界情况**：空值/空集合、异常与非活跃状态、查询失败降级、并发与重复执行，逐一自问；有答案写入设计，没答案进「待确认」清单。
4. **影响面**：涉及的规则或行为在代码库中是否有多处并存实现、是否有其他调用方依赖现状，确认过再给结论。
5. **内部一致性**：文档前后不自相矛盾（同一字段的类型/取值/默认值、同一流程的节点顺序在各章节保持一致）。每次审查 requirements、design、tasks 或其他 spec 文档时，都必须重新执行内部一致性复核，交叉检查同一业务概念、规则、字段、流程和边界条件在文档内部及文档之间是否一致；发现矛盾时不得直接输出通过或自行选择其中一种说法，应列出冲突位置和差异，交由我确认后再修订结论。

## 不明确时的处理方式

- **禁止用"合理默认值"填补空白**，也禁止用"应该""一般来说""通常""预计"这类模糊措辞掩盖不确定；不确定就是待确认。
- 把不明确点集中成「待确认问题」清单抛给我，每条包含：问题描述、候选方案（含各自影响与代价）、是否阻塞后续实现。
- 待确认项由**我**决定，不要自行拍板后继续推进设计或编码；确认结果回写到需求/设计文档对应位置。
- 一次性把待确认问题问全，不要挤牙膏式每轮只问一个，导致设计反复返工。
