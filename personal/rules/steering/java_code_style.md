# Java 代码风格规范

## 优先使用策略模式（避免堆叠 if-else / switch-case）

有明显业务维度划分（如按状态、类型、节点、渠道等分支处理逻辑），且各分支职责相对独立、可抽象为统一接口的场景，优先使用策略类（策略模式）组织代码，而非在单个方法内堆叠多段 if-else 或 switch-case。

判断准则：
- 分支数量较多（3 个以上），且每个分支的处理逻辑有一定复杂度（不是简单的字面量映射）
- 未来可能新增/调整分支（如新增一种状态、一种节点类型）
- 各分支逻辑可以收敛为同一组方法签名（如都需要 build/handle/approve 等相同动作）

拆分方式：
- 定义统一接口（如 XxxHandler），每个业务分支实现一个类，通过枚举/类型字段注册到统一入口（Dispatcher），由 Dispatcher 按类型分发，调用方只面向接口和分发器，不感知具体实现
- 简单的字面量映射（如枚举转文案、固定数值映射）不必上升为策略类，用枚举自身携带属性或简单 switch 即可，避免过度设计



## 多线程正确性规则

- 使用 `Semaphore`/`CountDownLatch` 等并发控制原语时，`release()`/`countDown()` 必须放在 `finally` 块中执行，避免异常路径下计数泄漏导致死锁。
- 捕获 `InterruptedException` 后，必须调用 `Thread.currentThread().interrupt()` 恢复中断标志，不要吞掉中断信号。
- 多线程并发写入的集合必须使用线程安全容器（如 `Collections.synchronizedList`、`ConcurrentHashMap`），禁止对普通集合做无保护的并发写入。

## 异常日志记录规范

- 记录异常日志时，异常对象（`Throwable`/`Exception`）必须作为日志方法的最后一个参数传入（如 `log.error("操作失败: {}", msg, e)`），以保留完整堆栈信息；不要仅拼接 `e.getMessage()` 到日志文本中而丢弃堆栈。


## 多级判空使用 Optional 链式处理

- 涉及多级属性的连续判空取值（如 `a.getB().getC().getD()` 这类链路，中间任一环节可能为 null），优先使用 `Optional` 链式调用（`Optional.ofNullable(a).map(A::getB).map(B::getC).map(C::getD).orElse(default)`），避免多层嵌套 `if (xxx != null)` 判断。
- 仅有单层判空（只判断一个对象是否为 null）时，不必强套 Optional，直接判空即可，避免过度设计。
- 需要在链路中间失败时提前返回/抛异常的场景，可用 `Optional.ofNullable(x).orElseThrow(...)` 或 `.filter(...)` 表达，不要用 Optional 包一层又立刻 `.get()` 破坏空安全语义。

## 注释简洁规则

- 写注释时尽可能简略，只补充代码本身不容易直接看出的意图、约束、边界或原因。
- 非核心逻辑、直白实现、显而易见的流程可以不写注释，避免注释噪音。
- 注释优先解释“为什么这么做”，不要大段重复代码已经表达清楚的“做了什么”。
- 方法级别注释统一使用 Javadoc 多行格式：
  ```java
  /**
   * 
   */
  ```
  不要使用单行方法注释。
- 方法体内的行内/块内注释统一使用 `//`，不要用 `/** ... */` 或单独的块级文档注释格式。

### 不要把设计文档的理由抄进代码注释

- spec / 需求 / 设计 / 任务文档里的**决策理由、方案对比、历史踩坑背景**，是给实现者做判断用的，判断完就留在文档里，**不要复制到代码注释**。典型反例：把「不使用枚举类型：某模块曾因 MyBatis-Plus 枚举映射未生效导致读取为 null」这类背景写到实体字段上——字段注释只需说明该字段的取值含义。
- 代码注释只保留**当下阅读这段代码时必须知道**的信息：非显而易见的约束、边界条件、易踩的坑。历史沿革、为什么没选另一个方案，属于文档。
- 由此派生的执行纪律：把任务拆给他人/子代理执行时，任务描述里的「理由」段落要明确标注是判断依据、**不是注释内容**；也不要在任务描述里写「加注释说明 X」，除非 X 是真正非显而易见的约束。
- 编码任务的完成标准里要包含「注释符合本规范」，与编译通过并列。只检查「编译通过 + 静态诊断无问题」查不出注释噪音，而注释与代码不同步比没有注释更误导人。

## 入参与出参对象规则

- 涉及方法入参、出参、任务参数、接口请求响应等对象时，尽可能使用承载字段的对象，不要直接用零散基础类型、`Map` 或临时 JSON 结构硬解析，除非场景非常简单且明确不值得抽对象。
- **按数据流向选择后缀，不要混用**：
  - **接收入参**用 `DTO` 或 `Request`：方法入参、接口请求体、任务参数、发给下游/第三方的请求。
  - **接收返回**用 `VO` 或 `Response`：方法返回值、接口响应体、下游/第三方接口的响应、页面展示对象。
  - 判断依据是「谁产生这个对象」：由调用方填充后传入的是入参对象；由被调方或外部系统产生、本方只负责读取的是出参对象。
  - 反例一：把第三方 API 的响应体命名为 `XxxDTO`。它是返回结果，应为 `XxxVO` 或 `XxxResponse`。
  - 反例二：把前端提交的表单命名为 `XxxVO`。它是入参，应为 `XxxDTO` 或 `XxxRequest`。
  - 同一份数据在不同流向上不要复用同一个类：入参与出参的字段集合往往会分叉，共用会迫使其中一侧携带无意义字段。
- 同一项目内 `DTO`/`Request` 与 `VO`/`Response` 各选一套后缀并保持一致，不要同一层里既有 `XxxDTO` 又有 `XxxRequest`。已有既定风格的项目沿用既有风格。
- 禁止在方法调用的入参位置直接写实时 SQL 查询、Mapper 查询或链式查询结果，先落本地变量，再传给下游方法，避免隐藏副作用和降低可读性。

## 优先重写原生方法，不另起平行方法

- 某个行为能通过重写语言/框架已有的方法表达时，就重写它，不要再定义一个语义相同的自定义方法。典型如：对象转字符串表达用 `toString()`，而不是另写 `toXxxString()`；相等性判断用 `equals()` / `hashCode()`；排序用 `Comparable.compareTo()` 或 `Comparator`。
- Spring 已具备的能力优先用框架扩展点，不要另写一套平行实现。典型如：参数校验用 JSR-303 注解 + `@Valid`，类型转换用 `Converter` / `Formatter`，请求前后处理用 `HandlerInterceptor` / `@ControllerAdvice`，事件通知用 `ApplicationEvent`，定时任务用 `@Scheduled`，事务用 `@Transactional`，启动初始化用 `ApplicationRunner` / `InitializingBean`。
- 例外：重写会破坏原方法的语义契约时（如 `toString()` 还需承担调试输出用途、`equals()` 语义会影响集合行为），保留独立方法，并在注释中说明原因。
