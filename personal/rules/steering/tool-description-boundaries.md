# 工具描述的边界条件规则

## 适用范围

凡是描述「一个工具怎么用」的场景都适用：

- 编写或修改 skill 的 `description` / `SKILL.md`、MCP 工具说明、steering 里对某个工具的说明。
- 公共工具类、SDK 封装、Feign 契约、框架扩展点的 Javadoc 与设计文档。
- 在回复、SOP、记忆中向我介绍某个工具/方法/接口的用法。

## 核心要求：先写「做不到什么」，再写「能做什么」

工具调用失败的根因，多数不是不知道工具能做什么，而是不知道它**不能做什么**。描述工具时，边界条件必须单独成段、逐条列出，不能只写能力：

1. **不做什么**：工具在哪些情况下静默不生效、只做了一半、或做的事和名字暗示的不一样。
2. **不接受什么输入**：取值范围、格式、编码、大小写、空值 / null、路径范围、长度上限。
3. **失败长什么样**：越界或输入不合法时是抛异常、返回空、返回业务错误码，还是静默放行。**静默放行与静默空结果必须显式写出**，这是最难排查的一类。
4. **与名字/直觉相反的行为**：例如「重命名」不改调用方、「校验」只校验部分分支。

能力描述保持简短；边界条件宁可多写一条。

## 抽象概念必须配具体示例

格式名、单位、编码、协议名这类抽象描述，读者（包括模型）容易按字面猜错。凡是出现抽象概念，紧跟一个**可直接照抄的具体值**：

- `timestamp：RFC3339 格式，例如 2024-03-15T14:30:00Z` 远比只写「RFC3339 格式」有效。
- 判断依据：描述里出现「XX 格式 / XX 编码 / XX 单位 / 时间戳 / 百分比 / 前缀 / 模板」等词，就必须配示例。
- 示例要能区分易混淆的相邻形态，必要时写一个反例：`秒级时间戳，例如 1791504000（10 位），不是毫秒 1791504000000`。
- 有输入就有输出时，给「输入 → 输出」成对示例，而不是只给一侧。
- 示例值必须是实测或可复算的真实值，不要编一个形似但算不出来的值；含密钥、账号等敏感信息的示例截断或用占位值。

| 抽象写法 | 补上示例后的写法 |
|---|---|
| 日期字符串 | `yyyy-MM-dd`，例如 `2026-10-09`；不接受 `2026/10/09`、`2026-10-09 00:00:00` |
| 秒级时间戳 | `EpochMilliUtil.parseStartSecond("2026-10-09", UTC)` → `1791504000`（10 位，非毫秒） |
| 私钥：PKCS#1 去头尾 Base64 | 例如 `MIICXQIBAAKBgQDd...`（以 `MIIC` 开头），不含 `-----BEGIN RSA PRIVATE KEY-----` 与换行 |
| 完整 offline tag | 例如 `offline___1001_2002_abc`（`offline___{offerId}_{affiliateId}_xxx`） |
| 佣金比例，百分数 | 佣金 1.50、金额 10.00 → `15`（表示 15%），不是 `0.15`，也不带 `%` |

## 写法

- 边界条件放在能力描述之后、用法示例之前，用独立小节或列表，标题明确（如「边界 / 不支持」）。
- 每条写成「条件 → 结果」：`传入非 offline 前缀的非空字符串 → 按 click_id 放行，不报错`。
- 有实测依据的写明实测结论；没实测过的标「未验证」，不要把推断写成边界。
- 文档标称的边界与实测不一致时，两者都写：「文档标称 X，实测 Y」。

## 实例（均为实测，来源：DramaReach 接入，2026-10-09）

| 工具 | 只描述能力时的写法 | 必须补上的边界 |
|---|---|---|
| `semantic_rename` | 重命名符号并更新全部引用 | 实测只改了方法声明（1 file / 1 edit），调用方未改；用完必须 grep 旧名并编译 |
| `smart_relocate` | 移动文件并自动更新 import | 会提示「No import references were updated」，类内引用与调用方需手改 |
| `read_file` / `read_files` | 读文件 | 只能读工作区与 `~/.kiro`，工作区外报 Access denied（需换 fastctx 工具或 Copy-Item 中转） |
| `fs_write` | 写文件 | 返回成功时内容可能尚未落盘：同一轮紧接着的 shell 命令读到 0 字节（实测等 2 秒后恢复正常）；供命令引用的文件写完先核对长度，或与执行命令分在不同轮次 |
| 基类 `fillOrderTag` | 按 click/offline 规则填归因 | 非 offline 非空值（如 `abc123`）→ 按 click_id 放行；空值 → 返回 true 但不设 tag；只有 offline 前缀缺字段（如 `offline___1001`）才返回 false |
| `EpochMilliUtil.parseXxxSecond` | 日期转秒级时间戳 | 只接受 `yyyy-MM-dd`（如 `2026-10-09`）；空白返回 null；格式错抛 `ServiceException`；1970 前负值按 floor 取整 |
| Hutool `SecureUtil.sign(alg, key, null)` | RSA 签名 | 私钥字符串 PKCS#1 / PKCS#8 都接受；PKCS#1 依赖 BouncyCastle 在 classpath（缺失时运行时失败）；格式宽松，不能用来做格式校验 |
| DramaReach chargeOrder 接口 | 分页拉充值订单 | `page` ∈ [1,100]、`page_size` ∈ [1,10000]，越界（如 `page=101`）返回 `code=1 "wrong number range setting"`（不在文档错误码表）；文档称跨度 ≤31 天，实测 90 天内放行、93 天起返回 100004 |
| MySQL MCP | 执行 SQL | 受 `sql-guard.json` 约束：只放行 SELECT/INSERT/CREATE/SHOW/DESCRIBE，UPDATE/DELETE 需人工执行 |

## 自检

描述完一个工具，自问四句，答不上来就补：

- 给它一个「看起来合理但不合法」的输入，会发生什么？
- 它在什么情况下返回成功、但实际没做完？
- 调用方最可能依赖、而它其实不保证的行为是什么？
- 描述里的每个格式 / 单位 / 编码，是否都跟了一个可照抄的具体值？
