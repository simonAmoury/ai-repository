# 记忆库（ai-repository memory）

跨会话、跨工具（Claude / Codex / Kiro 共用）的长期记忆存放处。由 `memory-sync` 规则约束
何时读写，由 `managing-memory` skill 约束具体格式与流程。

## 目录结构

```text
memory/
├── global/
│   └── lessons.md      # 全局级：跨项目通用的工作习惯类错误 / 反复纠错点（纳入版本库）
└── projects/
    └── <项目名>/
        └── <需求-slug>.md   # 业务需求级：核心逻辑、核心设计、该需求特有的坑（纳入版本库）
```

## 版本控制策略

- `global/`：提交，随 `git pull` 在各机器间同步。
- `global/` 与 `projects/` 均提交，随 `git pull` 在各机器间同步。

## 读写约定（摘要，完整见 managing-memory skill）

- 开始与某模块/需求相关的开发前：先查是否有相关记忆 → 读 → 按记忆中的 `code_anchors`
  读**当前最新代码**做交叉验证，输出「历史结论 vs 现状差异」，再动手。
- 任务完成时：沉淀核心业务逻辑、核心代码设计、踩坑与反复纠错点。
- 跨项目通用的错误写入 `global/lessons.md`；项目特有的坑写入对应项目记忆。

## 历史提交范围记忆的使用约定

部分项目记忆（约 56 个）采用「历史提交范围自动整理」格式，专门记录来自历史分支/标签的提交集合。
这类记忆**不虚构业务规则**，只保留可安全记录的证据（提交哈希、标题、影响文件、方法签名）。

### 识别特征

- front-matter 含 `tags: [git-history, ...]`
- "踩过的坑"章节含「本文由历史提交范围自动整理」

### 查阅方式

1. **提交标题是唯一已核对的历史业务描述**，标题之外的推断不可信。
2. **恢复业务规则的步骤**：
   - 先运行 `git show <hash>` 阅读完整变更
   - 再读取「核心代码设计」中标注「当前仍存在」的文件
   - 逐一比较 `<hash>^..<hash>` 与当前 `master`
   - 确认后再更新本记忆的 `code_anchors` 和核心业务逻辑
   - **不要把历史文件路径直接当作当前实现**
3. **当前路径不存在时**：只能通过提交哈希回溯，文件可能已改名或删除。
4. **同一标签可能包含功能、修复和代码整理**，必须以完整提交清单回看，不能只取首尾提交。

### 通用注意事项

- 历史改动文件在当前 `master` 上可能被后续需求覆盖，语义已漂移。
- 「提交内容证据」只摘录方法/类型声明，不保存密码/token 等敏感内容。
- 完整差异仍以提交哈希为准，本记忆只是索引入口。
