# 全局教训（跨项目通用）

> 记录**跨项目复用**的工作习惯类错误。每条教训是**一类问题**的抽象，不是一次事故一条；
> 具体事故作为「案例」挂在对应教训下，保留当时场景与正反做法。项目特有的坑写入
> `projects/<项目名>/<需求>.md`，不要放这里。
>
> - 新案例先找能归入的已有教训，追加到其「案例」里，必要时修订「问题本质 / 正确做法」使之覆盖新案例。
> - 只有现有教训都无法覆盖时才新增 `### L-XXX`。
> - 本文件会定期整理（合并、拆分、重排编号），项目记忆**不得引用**这里的编号。

## 条目格式

```markdown
### L-编号 抽象标题（一类问题 + 通用解法）
- 分类: 性能 / 数据访问 / 并发 / 流程 / 其他
- 问题本质: 为什么会犯这类错（认知/习惯层面的根因）
- 正确做法: 适用于这一类问题的通用做法
- 案例:
  1. 案例名（YYYY-MM-DD）
     - 场景: 当时在做什么
     - 反例: 具体错在哪
     - 正例: 应该怎么做
```

## 教训清单

### L-001 验收要对准真实目标，代理信号通过不等于完成
- 分类: 流程
- 问题本质: 把「容易得到的通过信号」（mock 测试全绿、编译通过、诊断为零、工具返回成功、对象层一致）当成「目标已达成」。代理信号只证明它覆盖到的那一层，覆盖不到的层（真实配置读取、落库、依赖方启动、调用方引用、CLI 行为）恰恰是最容易出错的地方。
- 正确做法:
  - 宣称完成前先问「真实目标是什么、当前证据覆盖到哪一层」，没覆盖到的层要么补验证，要么明确写「未验证」。
  - 配置/外部依赖类改动必须打通真实链路（回读入库值 + 打真实接口）；落库类改动要做落库级比对；共享模块改动要让依赖方至少启动一次；重构要先用表征测试锁定外部行为。
  - 测试 FAIL 先判断断言本身对不对；期望值用独立的标准实现现算，不手写字面量。
- 案例:
  1. 测试全绿但配置读取链路没验证（2026-08-06）
     - 场景: 改动依赖系统字典 / Apollo / DB 配置表 / Feign，单测把 `DictCache`、Feign、DB 全部打桩。
     - 反例: 用例全绿就宣称功能可用，没验证代码能否真读到库里的配置、字段名/code 拼没拼对、缓存会不会刷新。
     - 正例: 用 MCP/SQL 逐字符核对入库值，服务起来后打真实接口；二者缺一不能宣称可用。mock 测试只证明「给定输入下算法对」。
  2. 新旧实现「等价」只比到对象层（2026-08-11）
     - 场景: 重写一条定时同步链路，要证明新旧实现落库一致，表里没有批次号。
     - 反例: 只比「API 拉取 → 实体对象」逐字段一致就宣称对齐，没覆盖 upsert 分支、唯一键冲突、批内重复、事务边界；或按业务日期查表当基线，而 upsert 会就地更新旧行，事后无法区分。
     - 正例: 对象级、落库级都验。每次执行后 `CREATE TABLE <snap> AS SELECT ...` 固定快照，用 `LEFT JOIN` + `SUM(NOT (a.col <=> b.col))` 逐字段统计差异，同时统计两侧独占行数与业务键重复数。覆盖三种场景：旧实现落库、旧数据在库时跑新实现（验更新分支）、清表后跑新实现（验插入分支）。只允许 id/create_time/update_time 有差异，并在报告里写明。
  3. IDE 重命名/移动工具只改声明不改引用（2026-10-09）
     - 场景: 用 `semantic_rename` / `smart_relocate` 重命名方法、移动类。
     - 反例: 看到「Successfully renamed」就认为调用方已同步；实际 `1 file changed with 1 edit`，同类和跨模块调用方都没动；`smart_relocate` 提示「No import references were updated」也没注意。
     - 正例: 先核对工具报告的 changed files / edits 数是否与预期引用数相符；无论成功与否都全仓库 grep 旧名（含测试、XML、文档），最后对受影响模块（含 `compileTestJava`）编译。公共模块改名要提醒其他分支合并时会编译失败。
  4. 测试期望值手算错，测试自身的错被当成代码缺陷（2026-10-09）
     - 场景: 写对照测试，期望值是时间戳、金额等需要换算的量，断言里含「当前时间 ± N 秒」。
     - 反例: 手算 `1716700000` 为 `05:46:40`（实为 `05:06:40`）；时序断言用「调用后取 now」，首次签名初始化耗时 6 秒导致误报；`"0"` 与 `"0.00"` 用字符串比较。4 个 FAIL 里 3 个是测试自身的错。
     - 正例: 期望值用 JDK `Instant`/`LocalDate`、`BigDecimal.compareTo` 现算；时序断言用「调用前/调用后」区间夹逼；FAIL 时先逐条判定断言是否正确，再判定代码，结论分开报告。
  5. 共享模块新增类只编译了自己的服务（2026-10-09）
     - 场景: 在被多个服务依赖的 `xxx-api` 模块新增实体，依赖方服务里已有同简单类名的类。
     - 反例: 自己的服务编译通过就交付；依赖方启动时报 `TypeException: The alias 'CurrencyExchange' is already mapped`（MyBatis 按简单类名注册别名，包名不同也冲突），编译期完全发现不了。
     - 正例: 共享模块改动的验收除编译外，依赖方服务至少启动一次。
  6. 重构只跑单元测试，漏掉调用路径（2026-08-25）
     - 场景: 整理内部结构（抽公共逻辑、拆模块），要求 CLI 命令、输出文案、生成文件不变。
     - 反例: 抽公共逻辑后只搜了部分调用点，漏掉 Claude MCP 单独同步路径；测试用 `/ai-repository:begin/` 短子串统计 marker，规则正文新增同名说明后误报。
     - 正例: 重构前先写表征测试锁定生成文件内容、CLI 返回结构、规则优先级；断言匹配完整 marker 文本；抽公共逻辑后全局搜旧调用点逐处确认；阶段性跑全量测试 + 隔离仓库、独立 `AI_CONFIG_HOME` 的真实 CLI 集成验证。

### L-002 外部 API、库、框架、宿主的行为要实测，不按名字、文档、印象推断
- 分类: 其他
- 问题本质: 用常量名、方法名、文档数值、「通常都这样」的印象代替实测。名字和文档描述的是设计意图，实际行为常在边界值、重复调用、负数、链接目录这类非典型输入上偏离，而偏离往往是静默的。
- 正确做法:
  - 选 API 前先确认准确语义，拿不准就写最小示例实测，用边界值（起点和终点、负数、null、重复调用、超上限）而不是典型值。
  - 文档数值（上限、跨度、格式）落成常量前实测一次，常量注释写「文档标称 X，实测 Y」。同一文档里其他接口的结论不能套用。
  - 选错 API 时换 API，不要用循环重试等控制流去抵消语义差异。
  - 宿主扩展机制不生效时直接读宿主的扫描实现，不要反复重装试探。
  - 实测结论连同数据写进文档，避免下一个人再猜。
- 案例:
  1. 用 `get()` + while 重试模拟不可中断等待（2026-08-18）
     - 场景: 并发汇总需要不可中断地等子任务全部结束。
     - 反例: 凭印象选 `Future.get()`，发现它响应中断就在外面套 `while` 重试，把选错 API 变成控制流补丁。
     - 正例: `CompletableFuture.join()` 本身就是不可中断等待，返回前由 JDK 恢复中断标志。实测：300ms 中断主线程，join 仍在 2008ms 任务完成时返回，之后 `isInterrupted()` 为 true。
  2. `TimeUnit.toSeconds` 对负数截断（2026-10-09）
     - 场景: 新增「毫秒转秒」公共方法。
     - 反例: 用 `TimeUnit.MILLISECONDS.toSeconds`，它向 0 截断，1970 年前的负数毫秒比 floor 多 1 秒。
     - 正例: 与 JDK `toEpochSecond` 全量对照（含负数、边界、null）后改用 `Math.floorDiv`。公共工具方法新增或改名后都要拿原实现或标准库做对照。
  3. `ISO_INSTANT` 在区间终点输出纳秒（2026-08-20）
     - 场景: 按外部接口要求输出 ISO 8601 秒级时间。
     - 反例: 按名字选 `DateTimeFormatter.ISO_INSTANT`，只测了区间起点。`LocalTime.MAX` 输出 `...23:59:59.999999999Z`，被接口拒绝。
     - 正例: 用 `DatePattern.UTC_PATTERN`（实测为 `yyyy-MM-dd'T'HH:mm:ss'Z'`）+ `LocalTime.MAX.withNano(0)`。工具库常量的 pattern 字面量也要实测。
  4. 单测绕过框架入口，基类字段和 mock 参数类型按语义推断（2026-09-02）
     - 场景: 给继承框架抽象基类的定时任务写单测，直接调用业务方法。
     - 反例: 假设基类参数字段构造后即可用；score 参数按「时间戳」推断用 `anyLong()` verify；脱离 Spring 后 `LambdaQueryWrapper.select(SFunction...)` 抛异常被业务 try-catch 吞掉，表现为「mock 零交互」，误判为业务缺陷。
     - 正例: `javap -p -c` 确认字段赋值时机，只在入口方法赋值的用反射注入；verify 参数类型以方法签名为准（`zAdd` 的 score 是 `double`）；`@BeforeAll` 里 `TableInfoHelper.initTableInfo(...)`。
  5. 「失败码」带回有效数据，幂等重跑直接抛错（2026-09-11）
     - 场景: 对接「创建型但实际幂等」的接口（生成口令/邀请码），会重复调用同一组参数。
     - 反例: 统一按 `success != true` 抛异常，只用文档成功示例验证一次。同参数第二次调用返回业务失败码，功能在重跑时完全不可用。
     - 正例: 实测一次重复调用，逐字段看响应：常见形态是 HTTP 200 + 业务码非 0 + `success=false`，但 `data` 带回首次结果（如「already generated」）。把这种码定义成常量列入可接受状态，并实测唯一键由哪些请求字段构成。
  6. 第三方文档数值上限过时或口径相反（2026-09-11，2026-10-09）
     - 场景: 按文档实现分页、长度校验、时间窗口。
     - 反例: 文档写 pageSize 最大 50 就写死成常量，实测 200、500 都能返回满页，白发 4 倍请求。反方向：文档写「跨度不超过 31 天」，据此把代码「多放行 1 天」当缺陷修了，实测平台放行到 90 天。
     - 正例: 发一次超出文档值的请求看实际返回再定常量；按文档推出的「缺陷」宣称前也要实测，结论写成「代码按文档口径从严，平台实际更宽松」。
  7. 宿主扫描不认 Windows junction（2026-09-18）
     - 场景: skill 已用 junction 装进 `~/.kiro/skills`，文件系统确认在位，Kiro 始终看不到。
     - 反例: 反复重装、按名字硬激活、猜 frontmatter 格式或版本问题，把 junction 当成与实体目录等价。
     - 正例: 在 `<安装目录>/resources/app/extensions/**/dist/*.js` 里 grep `SKILL.md` 找到扫描实现：`readdir(withFileTypes)` + `if (!entry.isDirectory()) continue`，而 junction 在 readdir 里 `isDirectory()=false`，且只 warn 不抛错。改为实体复制（`fs.cpSync`）并配合 git hook 重装；修完重启宿主。
  8. 签名原文与实际请求不同源（2026-08-24）
     - 场景: 对接签名原文包含 query string 的第三方 API。
     - 反例: 签名用 DTO 拼接，请求走 UrlBuilder 自动编码，两边不一致导致验签失败；按习惯用 LF 作待签串分隔符。
     - 正例: 签名与请求使用同一个 query 字符串，原样拼接不二次编码；分隔符实测（Blibli 是 CRLF `\r\n`）；反射拼 query 的 DTO 不加非接口参数字段。

### L-003 SQL 与数据库工具有静默语义陷阱，写入和筛选前用边界值实测
- 分类: 数据访问
- 问题本质: 按其他语言（Java 字面量、字符串精确比较）或直觉理解 SQL 的转义、比较、截取语义，以及按表面信息（列名）理解数据库工具的返回。这些陷阱不报错，只产出错误数据。
- 正确做法:
  - 写库后回读逐字符比对；能走前端表单原文录入就走表单。
  - 前缀匹配、分段、按字符截取前，用边界值 SELECT 实测。
  - 判断对象是否存在只看返回的数据行，不看列名等元信息。
- 案例:
  1. 反斜杠、单引号双重转义（2026-08-06）
     - 场景: 把含反斜杠的正则写进字典表。
     - 反例: 按 Java 字面量转义直接拼 SQL；单个反斜杠被 MySQL 当未定义转义吞掉，入库字符串已损坏且无报错。
     - 正例: MySQL 字符串字面量里反斜杠还要再翻倍，单引号写 `''`；写库后回读逐字符比对。
  2. MCP 结果列名来自默认连接库（2026-08-11）
     - 场景: 通过 MySQL MCP 执行 `SHOW TABLES FROM other_db LIKE ...`，连接默认库是另一个库。
     - 反例: 看到列名 `Tables_in_<默认库>` 就判断查错库或表已存在，进而重复建表或放弃操作。
     - 正例: 完全限定名时作用库由语句决定，列名是噪音；存在性只看有没有数据行，需要确认库名另跑查询。
  3. PAD SPACE 比较与 `SUBSTRING_INDEX` 段数不足（2026-09-02）
     - 场景: 写修数脚本，按前缀筛选、按分隔符取第 N 段。
     - 反例: `LEFT(col, n) = '前缀 '` 做前缀匹配（`utf8mb4_general_ci` 下 `'offline' = 'offline '` 为 1，误命中更短的值）；段数不足时 `SUBSTRING_INDEX` 返回整串再取最后一段，「取第 4 段」拿到第 3 段，`<> ''` 挡不住。
     - 正例: 前缀用 `LIKE '前缀 %'`；取第 N 段前用 `LENGTH(x) - LENGTH(REPLACE(x, sep, '')) >= N-1` 校验段数；按字符位置截取用 `CHAR_LENGTH`。

### L-004 落库字段的值由约束、下游消费方、原始精度决定，不凭直觉设
- 分类: 数据访问
- 问题本质: 按「语义上合理」决定字段值（缺失留 null、状态照搬兄弟实现、取整后的金额算比例），没查目标列的 NOT NULL/默认值、没查下游过滤条件、没确认计算精度。结果批量写入失败、数据被静默跳过、派生字段失真。
- 正确做法:
  - 写库前查表结构（`IS_NULLABLE` + `COLUMN_DEFAULT`）和 `sql_mode`；NOT NULL 且无默认值的列必须给兜底值，兜底的业务语义要单独确认并在文档写明依据是 DB 约束。注意 ORM 字段策略（MyBatis-Plus 的 `insertStrategy=NOT_NULL` 让 null 字段不进 INSERT）。
  - 状态值、枚举映射先 grep 下游消费方（定时任务、下发、报表）的过滤条件，按「谁会取它」定值；参照兄弟实现要读完整套机制（快照、二次写入、后处理）。
  - 派生字段用未取整的中间值计算，各字段独立取整；验收样例必须包含「取整前后差异显著」的小额边界值。
  - 数据修正脚本的筛选条件与赋值字段必须从运行时代码的合法性判定反推，逐个边界值用 SELECT 模拟核对；修数前先看下游校验把依赖字段一并回填。预览 SQL 除了列「将被修改的行」，还要单独列「被排除的行」人工确认。
- 案例:
  1. NOT NULL 字段留 null 整批失败（2026-08-18）
     - 场景: 把外部接口响应映射成实体落库，源字段可能缺失。
     - 反例: 按语义决定「缺失留 null」，没核对目标列约束和 sql_mode；严格模式下插入报错，批量写入因事务回滚整批丢失，单测 mock DB 完全测不出。
     - 正例: 查表结构和 `SHOW VARIABLES LIKE 'sql_mode'`；确认 `insertStrategy` 默认行为；兜底值的业务语义单独确认。
  2. 照搬 inner_status 导致订单永不下发（2026-10-09）
     - 场景: 新接平台，状态字段参照同框架下已有实现。
     - 反例: 看到兄弟实现把「已支付」映射成 `CONFIRMED` 就照搬，没注意它能被下发靠另外补的 `pending_confirm` 快照；下游任务 `WHERE inner_status = 'pending_confirm'`，新平台订单永远不下发。
     - 正例: grep 字段在消费方的过滤条件和常量，按「谁会取什么值」定值；参照兄弟实现读完整套机制。
  3. 用取整后金额算比例（2026-10-09）
     - 场景: order_amount 按 2 位精度取整后落库，用它算 commission_rate。
     - 反例: JPY 10 × 0.007369 = 0.07369 → 取整 0.07，比例 71.43%（按原值应为 67.85%，偏差 5%）。
     - 正例: 派生字段用未取整中间值计算，各字段独立取整；验收样例包含小额边界值。
  4. 修数脚本筛选条件凭 SQL 直觉设（2026-09-02）
     - 场景: 写一次性修数 SQL，把历史错误数据改成代码现在会产出的样子。
     - 反例: 按 SQL 侧直觉设阈值（「至少 5 段才算完整」），没回读代码合法性判定，代码认为合法的记录被漏修；只改看起来错的两个字段，没补齐其他字段，改完卡在下游校验被静默跳过。
     - 正例: 阈值从代码合法性判定反推，逐个边界值 SELECT 模拟；修数前看下游校验逻辑把依赖字段一并回填；预览 SQL 列出被排除的行人工确认。

### L-005 判断仓库当前状态要查实际绑定、依赖树、既有先例，不凭记忆或名字推断
- 分类: 流程
- 问题本质: 用上一轮留下的印象、类名、知识库记录、「通常都有」的预期代替实际查询。代码改动（尤其用户在我两次操作间手动改的）、传递依赖、DI 绑定、既有先例这些不查就不知道。
- 正确做法:
  - 断言「没有某依赖/能力」前跑 `gradlew dependencies` 落盘 grep，同时查工具库。
  - 判断底层实现查全部实现的 `@Primary` / 条件注解、注入点声明（字段名匹配优先级低于 `@Primary`）；类名、包路径、注释都可能滞后；`@Deprecated` 只表示劝退新用法不代表行为变了；方法体里 `if (1 == 1) return` 类短路要读到。
  - 知识库记录的「既有事实」被用作「可以省略校验」依据时，动手前实测一次（DB 约束查 `information_schema`，配置查真实环境，框架行为写最小示例）；实测与记录冲突时以实测为准并回头修正源头记录。
  - 遇框架报错/冲突时先按关键字/注解名在仓库搜先例，有先例优先沿用并注明。
  - 跑测试前读当前代码，不凭上一轮记忆认定还是自己改完的样子。
- 案例:
  1. 断言「项目没有 BouncyCastle」不查依赖树（2026-10-09）
     - 场景: 需要解析 PKCS#1 私钥，印象里「项目没引入 BC」。
     - 反例: 只看了本模块 `build.gradle` 直接依赖没搜到就断言「未引入」，据此手搓 DER 包装改了四轮；用户问「有没有其他工具」才查，`bcprov-jdk15on:1.68` 早已传递引入，Hutool `SecureUtil.sign` 自动注册 BC。
     - 正例: 跑 `gradlew :<模块>:dependencies --configuration runtimeClasspath` 落盘 grep；查工具库是否已提供。
  2. 按类名、注释断定底层实现（2026-09-20）
     - 场景: controller 实际调哪个实现，类名带某下游名字、包路径按下游命名、注释写「底层调用 X」，还标 `@Deprecated`。
     - 反例: 据此断言读的是 X，新增一套平行契约读 Y；实际读 Y 的实现标 `@Primary`、读 X 的 `@Primary` 被注释，Spring 优先 `@Primary` 而非字段名；凭证映射 `if (1 == 1) return` 透传。
     - 正例: 查全部实现的 `@Primary` / 条件注解、注入点声明；类名、注释可能滞后；`@Deprecated` 不代表行为变；短路开关必须读到。
  3. 知识库记录的唯一约束实际不存在（2026-09-07）
     - 场景: 方案论证时引用 steering 记录的「表有 `code+dict_key` 唯一约束」。
     - 反例: 把二手记录当已验证事实写进设计、SOP，据此省掉代码重复检测并在 SOP 写「无需人工核对重复」；实测该表只有 `PRIMARY(id)`。
     - 正例: 被用作「可以省略校验」依据的事实动手前实测一次；实测与记录冲突以实测为准并回头修正源头。
  4. 遇别名冲突从原理设计方案（2026-10-09）
     - 场景: 共享模块新增实体，依赖方启动报 `The alias 'CurrencyExchange' is already mapped`。
     - 反例: 从原理设计方案（把实体挪进服务模块、改包名），没先搜仓库；`LogMfRedirect` 早已用 `@Alias("TradeLogMfRedirect")` 解决过相同问题。
     - 正例: 先按关键字在仓库搜先例，有先例优先沿用并注明；没先例再从原理设计。
  5. 凭上一轮记忆认定代码还是自己改的（2026-10-09）
     - 场景: 跑测试前，上一轮刚改完一段校验。
     - 反例: mock 测试 6 项失败，根因是用户在两轮间有意删了那段校验；我直接把校验加回去了。
     - 正例: 先读当前代码定位差异，再问用户「是否有意」。

### L-006 工具输出、表面现象不是事实本身，存在性、执行结果、根因都要取直接证据
- 分类: 流程
- 问题本质: 把「工具说的、显示的」当成地面事实:模糊搜索无结果就认定不存在、文件大小差值恰好等于行数就推断是换行转换、工具返回成功就认为引用已更新、0 字节文件在写完瞬间就认定写入失败。工具输出只反映工具看到的那一层，不反映文件系统状态、延迟落盘、用户中途改动。
- 正确做法:
  - 判断文件/目录是否存在用 git 命令或精确路径读取，不用模糊搜索工具的「无结果」。
  - 大小/数量差异恰好「说得通」时先取直接证据（比 mtime、`Buffer.equals` 逐字节、看内容差异）再解释成因。
  - 命令报「找不到任务/类」这类与脚本内容相关的错误时，第一步先 `(Get-Item <file>).Length` 或读回文件确认内容在。
  - shell 回显残缺、为空、乱码时先认清环境（代码页、stdout 捕获只回尾部）再判断，落盘复核结果而不直接重试有副作用的命令。
- 案例:
  1. 模糊搜索无结果误删目录（2026-09-07）
     - 场景: 要删临时测试目录 `src/test`，用 `file_search` 模糊搜索无匹配。
     - 反例: 把「无匹配」当成「不存在」，`Remove-Item -Recurse` 整个目录，删掉了两个既有测试文件。
     - 正例: 删目录前 `git ls-tree HEAD <dir>` 列出被跟踪文件；模糊搜索「无结果」只说明没搜到，判断存在性用 git 或精确读取；宁可只删明确记得创建的文件路径，不对目录递归删。
  2. 文件大小差 117 字节恰好约等于行数（2026-09-18）
     - 场景: 复制文件后校验，差 117 字节而文件约 117 行。
     - 反例: 用巧合直接推断是 LF→CRLF，把假设当结论写进汇报。
     - 正例: 比 mtime、`Buffer.equals` 逐字节、落盘看内容差异；真实原因是用户在两次操作间自己改了源文件（版本 1.2.0→1.3.0）。
  3. Gradle init 脚本 0 字节被当成写入失败（2026-10-09）
     - 场景: fs_write 写 init 脚本，紧接着执行，报「Task not found」。
     - 反例: 反复重跑命令、怀疑 Gradle 缓存；实际执行瞬间文件 0 字节。进一步实测:返回成功后立即 `Length` 为 0，`Start-Sleep 2` 后 3808 字节——延迟落盘。
     - 正例: 报脚本内容相关错误时第一步先 `Length` 或读回确认内容在；写文件与执行引用它的命令不放同一轮并行。
  4. shell 回显残缺被判定为挂住（2026-08-10）
     - 场景: Windows 控制台（代码页 936/GBK）执行命令，回显为空、只有尾部、或乱码。
     - 反例: 认定挂住立即重试，或构造更复杂的多行/带中文命令；多行命令停在续行提示符真的无响应。
     - 正例: 先认清环境（代码页 936、stdout 捕获残缺只回尾部）；命令里不嵌中文（中文先写文件再 `Copy-Item`）；需要看输出就 `Out-File` 落盘；显式传 timeout；回显残缺时落盘复核而不直接重试有副作用命令。

### L-007 有副作用的操作要限定范围、按依赖顺序串行、不盲目重试
- 分类: 流程
- 问题本质: 副作用操作（删除、写库、install、调用外部接口）一旦执行就改变状态，重试前没确认幂等性、并行调用时没判断依赖关系、清理范围没限定在自己新建的文件。结果误删既有文件、延迟落盘导致依赖文件的命令读到旧内容、有副作用命令被重复执行。
- 正确做法:
  - 删除前用 `git status` / `git log` 核实；HEAD 中已存在的一律不动；批量删前列清单说明判定依据；删整个目录前 `git ls-tree HEAD <dir>` 列出被跟踪文件；误删用 `git checkout -- <path>` 或 `git show HEAD:<path>` 原样恢复，绝不凭记忆重写，恢复后 `git diff` 确认零差异。
  - 有先后依赖的工具调用一律分轮串行，并行只用于彼此无依赖；写文件与执行引用它的命令分轮。
  - 回显残缺、看起来挂住时先落盘复核，不直接重试有副作用命令（写库、删文件、install）。
  - 中文内容先写工作区文件再 `Copy-Item` 中转，不用 `Add-Content`/`echo` 按 GBK 编码损坏原文。
- 案例:
  1. 凭文件名像临时文件就删（2026-08-10，2026-09-07）
     - 场景: 任务收尾清理，或用户说「删掉测试」，仓库里有既有 `Test.java`。
     - 反例: 凭名字、凭「印象里是我建的」就删；把「去掉 X」扩大解释为仓库内所有同类；误删后凭记忆重写导致长行折断产生差异。
     - 正例: 删前 `git status` 核实；HEAD 中已存在不动，作用域默认只限本次任务产出；误删用 `git show HEAD:<path>` 原样恢复，`git diff` 确认零差异。
  2. 写文件与执行引用它的命令并行（2026-10-09）
     - 场景: 把「Copy-Item 源文件」和「依赖该文件的 install 脚本」放同一轮并行调用。
     - 反例: install 可能读到旧内容，只能串行重跑一次。
     - 正例: 有先后依赖一律分轮串行。

### L-008 范围和决策权始终归属用户：不擅自添加需求外逻辑，遇歧义先确认，有选项让用户选
- 分类: 流程
- 问题本质: 自行补充用户没提的兼容、兜底、回落分支；把格式类描述的多种合理解读选一种就动手；抽象层存在理由消失后以「将来可能用」保留；列出选项后把用户补充信息当成「继续」自己挑一个实施。超出授权范围的改动事后要回退，格式理解偏差要来回改。
- 正确做法:
  - 需求只给一种形态时只实现那一种，其他情况明确失败；每个兜底分支要能答出「需求依据是哪一句」。
  - 格式类指令有多种解读时先把拟落库字符串开头几十字符 + 处理方式发给用户确认再动手。
  - 抽象层（基类、接口）删减到只剩一个使用方时当场合并回具体类，「将来可能扩展」不是保留理由。
  - 列出选项后，用户补充信息先用新信息复核各方案再交回用户选择；只有用户明确选定或明确说「你决定」时才实施。
- 案例:
  1. 自行加多格式兼容和回落（2026-10-09）
     - 场景: 实现私钥解析，想到「万一平台给另一种格式/字段缺失怎么办」。
     - 反例: 自行加 PKCS#1/8/PEM/裸 Base64 全支持、金额「A 缺失回落 B 并切换币种」、币种兜底，无需求依据；用户要求去掉，被问「来源」只能承认自己设计。
     - 正例: 只给一种形态时只实现那一种；担心的异常列进「待确认」问用户；每个兜底要能答出依据。
  2. 私钥格式指令歧义来回四轮（2026-10-09）
     - 场景: 用户说「存提取后的内容」，可理解为 PEM 全文 / 去头尾 Base64 / 转换后编码。
     - 反例: 按自己理解把 PKCS#1 转 PKCS#8 再存，写完代码、SQL、文档才交付；用户看到 SQL 值与给的不一致追问后又改，来回四轮。
     - 正例: 多种解读时先把拟落库字符串开头几十字符 + 处理方式发给用户确认。
  3. 删到只剩一个子类仍保留抽象基类（2026-10-09）
     - 场景: 为多子类抽了基类，随后删接口只剩一个子类返回常量。
     - 反例: 保留抽象基类和抽象方法，被问「为什么包一层」才意识到无存在理由。
     - 正例: 每次删减子类、接口、分支后回看抽象是否还有 ≥2 使用方；只剩一个就合并。
  4. 列选项后把补充信息当授权（2026-10-09）
     - 场景: 上一轮列出 A1/A2/B 方案请用户选，用户下一条只回了报错信息没说选哪个。
     - 反例: 把补充当「继续」自己挑 A1 直接改代码、删文件、改文档；用户实际选了另一种，只能回退。
     - 正例: 用户补充信息后用新信息复核各方案，交回用户选择；只有明确选定或说「你决定」时才实施。

### L-009 文档与决策要保留原始信息、写到可执行粒度、改完通读自洽
- 分类: 流程
- 问题本质: 改写文档时只关注「新结论」，丢掉原始表格、示例这类精确验收依据；只读规则不读示例；决策只写类别不写具体实例；把格式诊断为零当成内容自洽；日期沿用会话里推算过的值。每处单看都自洽，所以不会触发怀疑。
- 正确做法:
  - 重写章节时先把原表格、示例逐条搬过来再改语义；外部需求的示例列逐字提取，它往往比规则列更精确。
  - 涉及共享资源的决策写到具体 bean 名、配置 key、队列名、容量参数，并写「为什么不用现成的」；自问「照这条实现会不会有第二种合理解释」。事后补细化要显式记录原结论缺了什么。
  - 格式诊断只查结构，改完必须通读交叉核对（决策表 vs 正文、术语表 vs 用例、示例 vs 规则）。
  - 写日期时每次从环境的当前日期现取，收尾把产出物里所有日期与当前日期对一遍。
- 案例:
  1. 重写章节时示例表被压成一句话（2026-08-06）
     - 场景: 配置模型从「多子项」改成「单条」，需要重写带示例的表格。
     - 反例: 把表压成一句结论，丢掉示例列，后续反复回溯原始需求。
     - 正例: 先逐条保留原表，再在其上改语义。
  2. 只读规则列误解意图（2026-08-06）
     - 场景: 外部需求用「放行格式」和「示例」两列描述同一约束。
     - 反例: 只读规则列下结论；规则写「放行格式=空格」，但示例里没有空格，真正的空格在另一处完整链接里。
     - 正例: 逐字提取示例列，以示例为精确意图。
  3. 诊断为零但文档自相矛盾（2026-08-06）
     - 场景: 改完 requirements/design/tasks 后跑格式诊断。
     - 反例: 诊断为零就输出通过；实际「决策表说额外放行、正文说基础集已含」自相矛盾。
     - 正例: 改完通读并交叉核对决策表、正文、术语表、示例。
  4. 决策只写「由线程池容量决定」（2026-08-18）
     - 场景: 设计文档记录并发拉单的决策。
     - 反例: 没写用哪个池，实现按项目规范注入共享 `threadPoolTaskExecutor`，与其他业务抢线程；文档和 review 都看不出问题，因为字面上符合决策。
     - 正例: 写到具体 bean 名和容量参数，以及不用共享池的理由。
  5. 整个会话沿用错误日期（2026-09-14）
     - 场景: 在 SOP、审计日志、记忆里写实测日期，并据此构造 API 探测窗口。
     - 反例: 把 09-14 全程写成 09-11，SOP 两处、审计日志四条都错，探测窗口也错。
     - 正例: 每次写日期从环境现取，不复用上文出现过的日期字面量。

### L-010 注释、防御代码、review 结论要按「它解释或保证了什么」判断，不按「现在会不会触发」判断
- 分类: 流程
- 问题本质: 注释写进了不该写的东西（决策理由、历史沿革），又用错误的标准删该留的东西（用「当前链路不会触发」否定防御代码）；review 把做对一半的动作写成优点，位置引用不复核。根因都是没分清代码/注释/结论在解释哪个层次的问题。
- 正确做法:
  - 代码注释只留当下读这段代码必须知道的约束、边界、坑；决策理由和方案对比留在文档。派发任务时标明「理由段落是判断依据、不是注释内容」，并把「注释符合规范」写进完成标准。具体指令会压过抽象规则。
  - 判断防御代码是否多余，先分清它解释的是「方法自身要维持的不变量」还是「全链路风险」。否定它必须证明「即使上游改动这个位置也没有意义」。
  - 配置校验放在数据判空、提前 return 之前，配置错误不能因「恰好无数据」被吞掉。
  - review 的每条优点都要问「是否完整达成了它声称的目标」；位置引用用「类名 + 方法名」不写行号，完稿后抽查能否定位。
- 案例:
  1. spec 决策理由被抄进代码注释（2026-08-10）
     - 场景: 按 spec/tasks 实现，任务描述带「为什么这么选」，拆给子代理执行。
     - 反例: 执行者把理由抄成注释（「不用枚举：某模块曾因枚举映射未生效读取为 null」）；完成标准只有编译 + 诊断，查不出注释噪音。
     - 正例: 派发时标明理由不是注释内容；注释规范写进完成标准；review 单独过一遍注释。
  2. 用「当前链路不会触发」否定防御注释（2026-09-14）
     - 场景: review `parseOrders` 开头「配置校验先于数据判空」的注释。
     - 反例: 以「client 的 `of()` 一定先抛异常、走不到这里」断言注释不成立；实际它解释的是这一行为什么在 `isBlank(responseBody)` 提前 return 之前，价值在于不依赖调用方行为。
     - 正例: 先分清局部位置安排与全链路风险；解释决策的注释不能用事实核查推翻。
  3. 配置错误被「无数据」掩盖（2026-08-24）
     - 场景: 拉取外部订单，ext_config 可能缺 currency 等关键字段。
     - 反例: 先判 `data` 空就 return，「配置缺 currency + 当前窗口无订单」时账号被判成功。
     - 正例: 配置校验前置到数据判空之前，配置错误必须失败。
  4. review 把半个正确动作写成优点，行号对不上（2026-08-18）
     - 场景: 写 code review 报告，既列问题也列优点。
     - 反例: 把「捕获 `InterruptedException` 后恢复中断标志」写成优点，没看到它恢复后直接返回、没等剩余任务；238 行的文件引用到 `:697`。

### L-011 对接外部平台先找「填错不报错」的静默失败项，指针类规范要读原文
- 分类: 流程
- 问题本质: 只防显式失败（缺失抛异常），对「值合法但语义错」不做区分，上线后返回空数据被当成「没有业务数据」；规则里「套用 X skill」的一句提示被当成规范全文，工具列表为空被当成「不存在」。共同点是把「没报错、没看到」当成「没问题」。
- 正确做法:
  - 接入前逐个配置项自问「填错但格式合法时，接口报错还是静默返回空」。静默失败项写进 SOP：正确取值、错误取值长什么样、「返回 0 条先查这一项」；代码注释只写约束。
  - 调用内部接口时顺着调用链确认每个入参确实传到底层，DTO 有这个字段不代表生效。
  - 规则里出现「套用 X skill」时先把 skill 文件找出来读完；查用户级安装目录和 ai-repository 的 `company/skills/`、`personal/skills/`。工具列表为空只说明宿主没扫到，有无以文件系统为准。仿照既有产物是最后手段，且要先确认它合规。
- 案例:
  1. CJ 的 CID 填成 PID 只返回 0 条（2026-08-20）
     - 场景: 对接 CJ，配置里有多个语义相近的数字 ID。
     - 反例: 只把缺失校验写足；`publisherCid` 填成 `websiteId`（PID）不报错只返回 `count: 0`，被当成账号无数据白排查。
     - 正例: 逐项自问静默失败可能，SOP 写明正确取值与排查顺序；注释写「必须是公司 CID 不是 PID」。
  2. skill 只读了规则里的半句提示（2026-09-14）
     - 场景: 规则写「按 X skill 规定的结构执行」并附一两句要点，工具侧 skill 列表为空。
     - 反例: 把括号要点当全部规范，仿照一份既有产物写上线 SOP，写成七节 130 行；skill 实际规定四节 + 勾选式自检 + 固定文件名，仿照的产物本身也不合规范。
     - 正例: 先在文件系统找到 skill 读完，`resources/` 下的模板一并看；不一致时以 skill 为准并提出来。
