# 全局教训（跨项目通用）

> 记录**跨项目复用**的工作习惯类错误与反复纠错点，避免再犯。项目特有的坑请写入
> `projects/<项目名>/<需求>.md`，不要放这里。
>
> 每条一个 `### L-XXX` 小节，编号递增、不复用。新增时在文末追加。

## 条目格式

```markdown
### L-编号 一句话标题
- 分类: 性能 / 数据访问 / 并发 / 流程 / 其他
- 触发场景: 什么情况下我会犯这个错
- 错误做法: 具体错在哪
- 正确做法: 应该怎么做
- 首次记录: YYYY-MM-DD
```

### L-001 测试全绿 ≠ 功能可用，配置/外部依赖类改动必须实测真实读取链路
- 分类: 流程
- 触发场景: 改动依赖外部配置（系统字典 / Apollo / DB 配置表）或外部接口（Feign / 中间件）时，用单测把这些依赖全 mock 掉后测试全过
- 错误做法: 单测把 `DictCache`、Feign、DB 读取全部打桩，用例全绿就宣称功能可用；实际没验证「代码能否真读到库里的配置、字段名/code 拼没拼对、缓存会不会刷新」
- 正确做法: 配置/外部依赖类改动必须实测真正把代码和外部连起来的链路：① 用 MCP/SQL 逐字符核对入库值；② 服务起来后打真实接口。二者缺一不能宣称可用。mock 测试只证明「给定输入下算法对」
- 首次记录: 2026-08-06

### L-002 重写含表格/示例的文档章节，先把原表逐条搬过来再改语义
- 分类: 流程
- 触发场景: 需求/设计文档里某张带示例的表格，因方案调整需要重写（如配置模型从「多子项」改成「单条」）
- 错误做法: 顺手把带示例的表压成一句话或替换成新结论，丢掉示例列 / 精确验收依据，导致后续反复回溯原始需求
- 正确做法: 重写章节时先把原文档的表格/示例逐条保留搬过来，再在其上改语义；示例是精确验收依据，不能在重写中蒸发
- 首次记录: 2026-08-06

### L-003 外部需求（图片/飞书/文档）的「示例」列往往比「规则」列更精确，要逐字提取
- 分类: 流程
- 触发场景: 外部需求用「规则/放行格式」和「示例」两列并列描述同一条约束
- 错误做法: 只读「规则」列就下结论，忽略示例列
- 正确做法: 逐字提取示例列，它往往才是精确意图。曾出现「放行格式=空格」但示例里没有空格、真正空格在另一处完整链接里的情况，只读规则列会误解意图
- 首次记录: 2026-08-06

### L-004 spec/需求/设计文档的格式诊断只查结构，不查语义矛盾，改完必须通读交叉核对
- 分类: 流程
- 触发场景: 改完 requirements/design/tasks 后跑格式诊断（如 get_diagnostics）为零，就认为文档没问题
- 错误做法: 把「诊断为零」当成「内容自洽」，直接输出通过
- 正确做法: 诊断只查章节标题齐不齐，不查语义矛盾。改完必须通读并交叉核对（决策表 vs 正文、术语表 vs 用例、示例 vs 规则）；曾出现「决策表说额外放行、正文说基础集已含」自相矛盾而诊断为零
- 首次记录: 2026-08-06

### L-005 MySQL 写入含反斜杠/单引号的字符串有双重转义坑，优先走前端表单录入
- 分类: 数据访问
- 触发场景: 把含反斜杠的正则、含单引号的字符串写进 MySQL（如字典/配置表）
- 错误做法: 按 Java 字面量的转义直接拼进 SQL；只写单个反斜杠，被 MySQL 当未定义转义序列吞掉，入库字符串已损坏且无报错
- 正确做法: Java 字面量 `\\[`，MySQL 字符串字面量还要再翻倍 `\\[`，单引号写 `''`；写库后必须回读逐字符比对确认未被吞掉。能走前端表单/字典页按原文录入就走，可绕开双重转义坑
- 首次记录: 2026-08-06
### L-006 清理/删除只针对本次任务自己新建的文件，误删后必须用 git 原样恢复
- 分类: 流程
- 触发场景: 任务收尾做清理回收，或用户说「把 X 去掉」「删掉测试」时，仓库里存在看起来像临时产物的既有文件（名为 `Test.java`、`tmp_*`、内容是一段 main 方法或被注释掉的代码）
- 错误做法: 凭文件名像不像临时文件、凭「印象里是我建的」就删；把用户的「去掉 X」扩大解释为仓库内所有同类文件。误删后又凭记忆/命令回显重写文件内容，导致长行被折断、与原文件产生差异
- 正确做法: 删除前先用 `git status` / `git log` 核实——只要 HEAD 中已存在就是既有文件，不属于本次清理范围，一律不动；作用域默认只限本次任务产出，有歧义先问。批量删除前列出待删清单并说明判定依据。误删既有文件用 `git checkout -- <path>` 或 `git show HEAD:<path>` 原样恢复，**绝不凭记忆重写**，恢复后用 `git diff` 确认为零差异
- 首次记录: 2026-08-10

### L-007 命令「卡住」多半是 shell 输出残缺导致的误判，回显不可信时先落盘复核再判断
- 分类: 其他
- 触发场景: 在 Windows 控制台（代码页 936/GBK）执行命令，回显为空、只有尾部片段、或出现乱码，看起来像命令挂住了
- 错误做法: 认定命令卡住就立即重试，或改去构造更复杂的多行/带嵌套引号/含中文正文的命令；结果多行命令在交互式会话里停在续行提示符等输入，真的长时间无响应。也曾直接用 `Add-Content`/`echo` 把中文写进文件，按 GBK 编码损坏原文件
- 正确做法: 先认清环境事实——控制台代码页 936 非 UTF-8；stdout 捕获残缺基本只回传尾部（`Write-Output "A"; cmd /c echo B` 只回 B、`dir /a` 只回汇总行）；命令行会被截断且嵌套引号会失败。规避：命令里绝不嵌中文（中文内容先写工作区文件再 `Copy-Item` 中转）；需要看输出就 `Out-File` 落盘 + 读文件；一条命令只做一件事不用 `;` 串联；每次调用显式传 timeout；文件/搜索优先用专用工具而非 shell。回显残缺时先落盘复核执行结果，**不要直接重试**有副作用的命令（写库、删文件、install）
- 首次记录: 2026-08-10
### L-008 spec 文档里的决策理由不要抄进代码注释，注释规范要进验收门槛
- 分类: 流程
- 触发场景: 按 spec / tasks 文档实现编码任务，尤其是把任务拆给他人或子代理执行时；任务描述里带有「为什么这么选」的理由段落
- 错误做法: 把任务描述中的决策理由、历史踩坑背景原样传给执行者，执行者顺手把它抄成代码注释（如实体字段上写「不用枚举：某模块曾因枚举映射未生效读取为 null」）；任务描述里直接写「加注释说明 X」；完成标准只有「编译通过 + 静态诊断无问题」，查不出注释噪音；code review 只看正确性、跳过注释
- 正确做法: 派发任务时明确标注「理由段落是判断依据、不是注释内容」，不写「加注释说明 X」除非 X 是真正非显而易见的约束；代码注释只留当下读这段代码必须知道的约束/边界/坑，历史沿革与方案对比留在文档；把「注释符合规范」写进编码任务的完成标准，与编译通过并列；review 时单独过一遍注释。**具体指令会压过抽象规则**——泛泛要求「遵守 steering 规范」挡不住自己在同一段提示里给出的具体反例指令
- 首次记录: 2026-08-10

### L-009 新旧实现「等价」只算到对象层不够，落库等价要靠执行前后的快照表固定基线
- 分类: 数据访问
- 触发场景: 重写/重构一条已有的数据写入链路（定时任务、同步逻辑、导入器），需要证明新实现与旧实现落库结果一致；而表里没有批次号/任务执行 ID 可区分「本次写入」
- 错误做法: 只跑到「API 拉取 → 转换成实体对象」这一层做逐字段比较，就宣称新旧完全对齐——没覆盖 upsert 分支、唯一键冲突、批内重复、事务边界；或直接按业务日期查表当基线，而 upsert 会就地更新旧行，事后无法区分本次新增、本次更新与历史遗留
- 正确做法: 明确区分「对象级等价」与「落库级等价」，两者都要验。无批次号时用 `CREATE TABLE <snap> AS SELECT * FROM <表> WHERE <业务维度>` 在每次执行后固定一份快照，再用 `LEFT JOIN` + `SUM(NOT (a.col <=> b.col))` 逐字段统计差异（`<=>` 可正确处理 NULL），同时统计两侧独占行数与业务键重复数。至少覆盖三种场景：旧实现落库、旧数据在库时跑新实现（验更新分支，此时 id/create_time 应不变、只有 update_time 变）、清表后跑新实现（验插入分支）。业务字段差异应为 0，允许差异的只有 id/create_time/update_time 这类 DB 生命周期字段，报告里要把这点写明而不是笼统说「有差异」
- 首次记录: 2026-08-11

### L-010 数据库 MCP 的结果列名/元信息可能来自默认连接库，判断存在性只看数据行
- 分类: 数据访问
- 触发场景: 通过 MySQL MCP 执行跨库语句（`SHOW TABLES FROM other_db LIKE ...`、`other_db.table` 查询），连接本身配置的默认库是另一个库
- 错误做法: 拿返回的列名（如 `Tables_in_<默认库>`）当作语句实际作用的库，据此判断「查错库了」或「表已存在」，进而重复建表或放弃操作
- 正确做法: 语句里已用完全限定名时，作用库由语句决定，列名只反映连接的默认库、属于噪音。判断对象是否存在**只看有没有返回数据行**；需要确认作用库时另跑一条能返回库名的查询核对，不要靠列名推断
- 首次记录: 2026-08-11

### L-011 写库前先核对目标表的 NOT NULL/默认值与 sql_mode，映射留 null 会整批失败
- 分类: 数据访问
- 触发场景: 把外部报文/接口响应映射成实体落库，源字段可能缺失；用 `Optional...orElse(null)` 之类写法让缺失字段为 null
- 错误做法: 只按业务语义决定「缺失就留 null」，没核对目标列是否 `NOT NULL`、有没有默认值，也没确认库的 `sql_mode`；结果严格模式下插入直接报错，批量写入还会因事务回滚把整批数据一起丢掉，而单测把 DB mock 掉时完全测不出来
- 正确做法: 落库字段映射前先查一次表结构（列的 `IS_NULLABLE` + `COLUMN_DEFAULT`）和 `SHOW VARIABLES LIKE 'sql_mode'`。凡 `NOT NULL` 且无默认值的列必须给兜底值；注意 ORM 的字段策略（如 MyBatis-Plus 默认 `insertStrategy=NOT_NULL`）会让 null 字段**不进 INSERT 语句**，报错是 `Field 'x' doesn't have a default value` 而非 `Column cannot be null`，两种都失败。兜底值的业务语义要单独确认（金额取 0 无争议，费率/比例取 0 会与「真实 0%」混淆，需与需求方确认或改为跳过该条），并在文档写明兜底依据是 DB 约束
- 首次记录: 2026-08-18

### L-012 决策要写到「可执行」粒度，只写类别不写具体实例，实现必然按默认值走偏
- 分类: 流程
- 触发场景: 需求/设计文档里记录一条依赖具体资源的决策，如「用线程池并发」「走缓存」「用消息队列」「读配置中心」
- 错误做法: 决策只写到类别（「并发度由线程池容量决定」），没写用哪个线程池；实现时按项目通用规范就近注入了共享资源，与其他业务互相抢占，而文档、review 都看不出问题，因为字面上「符合决策」
- 正确做法: 凡涉及共享资源的决策，必须写到可直接落地的粒度：具体 bean 名 / 具体配置 key / 具体队列名 / 具体容量参数，以及「为什么不用现成的那个」。决策落库时自问一句「照这条描述去实现，会不会有第二种合理解释」，有就补细化。事后发现决策粒度不足时，回写文档要显式记录「原结论缺了什么、因此实现走了哪条路」，而不是悄悄改成新结论
- 首次记录: 2026-08-18

### L-013 用标准库/框架 API 前先确认其语义，别用循环重试等笨办法绕过
- 分类: 并发
- 触发场景: 需要某个特定语义的行为（不可中断地等待、超时控制、幂等重试等），手边有多个相似 API 可选
- 错误做法: 凭印象选一个 API（`Future.get()`），发现语义不符（它响应中断）就在外面套 `while` 循环重试来抵消，把「选错 API」变成「用控制流打补丁」，代码复杂度上升且意图被掩埋
- 正确做法: 先花一分钟确认候选 API 的准确语义再选：`CompletableFuture.join()` 本身就是不可中断等待，且被中断时会等到任务结束、返回前由 JDK 自行恢复中断标志，无需手工 `Thread.currentThread().interrupt()`；`get()` 才是可中断的。语义拿不准就写最小示例实测（本次实测：300ms 中断主线程，join 仍在任务完成的 2008ms 才返回，返回后 `isInterrupted()` 为 true），把实测结论连同数据写进文档，别让下一个人再猜
- 首次记录: 2026-08-18

### L-014 code review 的位置引用与「做对的事」都要复核，半个正确动作不算优点
- 分类: 流程
- 触发场景: 产出 code review 报告，既列问题也列做得好的地方；引用代码位置时顺手写行号
- 错误做法: ① 把「做对一半」的实现写进优点栏——如「捕获 `InterruptedException` 后正确恢复中断标志」，却没看到它恢复标志后直接返回、没等剩余任务结束，缺陷被优点掩盖，读者不会再去查；② 用行号标注位置，实际行号与文件严重不符（238 行的文件引用到 `:697`），导致无法定位、也暴露报告没经过复核
- 正确做法: 写进「做对的事」的每一条，都要问「这个动作是否完整达成了它声称的目标」——恢复中断标志只是合规的一半，另一半是不能提前退出。位置引用统一用「类名 + 方法名」，不写行号（行号在改动中必然漂移，且无法自证准确）。报告完稿后抽查几条引用能否定位到，定位不到的一律重写
- 首次记录: 2026-08-18

### L-015 对接外部平台先问「哪个配置传错了不会报错」，静默失败项要写进 SOP
- 分类: 流程
- 触发场景: 对接第三方 API，配置里有多个 ID 类字段（账号 ID / 公司 ID / 站点 ID / 应用 ID），语义相近且都是数字串
- 错误做法: 只关注「配置缺失会抛异常」这类显式失败，把校验写足就认为配置安全；对「值合法但语义错」的字段不做区分，上线后接口返回空数据，被当成「账号没有业务数据」白排查
- 正确做法: 接入前逐个配置项自问「填错但格式合法时，接口会报错还是静默返回空」。静默失败项必须：① 在 SOP 里写明正确取值、错误取值长什么样、以及「返回 0 条时先查这一项」的排查顺序；② 代码注释只写约束（如「必须是公司 CID 不是 PID」），排查话术留在 SOP。本次实例：CJ 的 `publisherCid` 填成 `websiteId`(PID) 不报错、只返回 `count: 0`，令牌与 CID 不对应同样如此
- 首次记录: 2026-08-20

### L-016 时间格式化常量要用边界值实测，别按常量名推断
- 分类: 其他
- 触发场景: 需要按外部接口要求的格式输出时间（如 ISO 8601），手边有 JDK 内置 formatter 与工具库常量多个选择
- 错误做法: 按名字选 `DateTimeFormatter.ISO_INSTANT`，认为「ISO 就是 ISO」；用区间起点测试通过就定稿，没测区间终点
- 正确做法: 用**边界值**实测再定。实测 `ISO_INSTANT` 格式化 `LocalTime.MIN` 输出 `2026-08-01T00:00:00Z` 正常，但 `LocalTime.MAX` 输出 `2026-08-20T23:59:59.999999999Z` 带纳秒，会被要求秒级精度的接口拒绝；改用 `DatePattern.UTC_PATTERN`（实测 pattern 为 `yyyy-MM-dd'T'HH:mm:ss'Z'`）+ `LocalTime.MAX.withNano(0)`。工具库常量的 pattern 字面量也要实测确认，不要凭常量名推断
- 首次记录: 2026-08-20
